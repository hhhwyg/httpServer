# HTTP 性能优化历程

本文记录本轮针对 `GET /ping` 吞吐问题的排查和优化过程。数字来自 WSL2 本机实测，不是生产容量承诺；除特别说明外，服务使用 Release 构建、6 个工作线程，客户端使用 512 个 Keep-Alive 连接和 4 个 C++ 客户端事件循环线程。

## 1. 问题现象

最初使用仓库内 Python asyncio fallback 测试 `/ping`，epoll 约 `7,645 req/s`，io_uring 约 `8,195 req/s`。增加客户端连接数后 QPS 基本不再上升而 p99 恶化，服务端 CPU 也没有接近机器的 12 个逻辑 CPU。结论是这组数字主要受单 asyncio 事件循环的客户端模型限制，不能作为服务器吞吐上限。

为排除客户端瓶颈，新增非阻塞 C++ epoll 客户端。它固定发送并校验完整的 `GET /ping` Keep-Alive 响应，只把正确的 `HTTP/1.1 200 OK` 计入成功数，并单独记录错误数。

## 2. 优化轮次

### Round 0：建立可用基线

- 保留 Python fallback，用于协议、延迟、短连接和资源指标。
- 增加 C++ 高吞吐客户端，避免把客户端单线程调度误判为服务端瓶颈。
- 初始 C++ 结果在不同 WSL 调度状态下约为 `196k～218k req/s`，说明服务器实际已经远高于 Python 测试显示的 8k。

### Round 1：绕过 `/ping` 通用业务路径

- `/ping` 使用编译期固定响应，跳过通用路由、应用回调队列和动态响应头序列化。
- 每个请求仍保留请求和响应指标计数，Keep-Alive 与短连接使用不同的正确响应。
- Keep-Alive 定时器不再每个请求都创建/取消 TimerNode，改为最多每秒刷新一次；连接关闭时仍然清理定时器。

### Round 2：降低解析成本

- `ChainBuffer` 对单块输入提供 `std::string_view`，普通请求不再复制整个输入缓冲区。
- `/ping` 请求头使用轻量扫描，不创建通用 header map；含 `Content-Length` 的请求继续走通用解析器，保留 body framing、重复字段和数字校验。
- 固定的 `GET /ping HTTP/1.0/1.1` 请求行直接在缓冲区中识别，避免创建 method、target、version 三个临时字符串。
- 对 `Connection` 的默认行为与原通用解析器保持一致：无字段时 HTTP/1.1 默认 Keep-Alive，有字段时只有包含 `keep-alive` 才保持连接。

### Round 3：减少缓冲区和事件循环分配

- 单块响应直接使用 `write()`，多块响应仍保留原来的 `writev()` 路径。
- 消费完数据后保留一个空 `BufferChunk` 给同一连接复用，避免每次 Keep-Alive 请求触发内存池全局 mutex 和分配/释放。
- epoll 正常事件循环直接遍历内核返回的事件数组，保留 `poll()` 快照接口供测试和诊断使用，避免每轮创建临时 `vector<shared_ptr>`。
- 对新增路径修正协议边界和成员初始化顺序，并用 sanitizer 回归。

### Round 4：补全 io_uring 批处理和高吞吐观测

- io_uring 的 CQE 指针数组改为构造时分配、事件循环重复使用，避免每次收割完成事件都分配 `queueSize_` 个指针。
- 使用 `io_uring_submit_and_wait()` 合并提交和等待动作，保留一次收割多个 CQE 的逻辑；`EINTR` 继续重试。
- C++ 基准客户端增加按请求延迟直方图、p50/p95/p99、服务端所有线程 CPU 时间、单核/整机 CPU 占用、RSS 和上下文切换采样。
- 修复带服务端 PID 时客户端线程参数被错误忽略的问题，并修正重连时复用旧连接状态的问题。

## 3. 结果记录

### 高吞吐 C++ 客户端

命令形式：

```bash
/tmp/httpserver-codex-bench-20260830/httpserver_epoll_benchmark \
  PORT 512 DURATION_SECONDS 4 SERVER_PID
```

同一环境下的代表性结果：

| 阶段/后端 | 服务线程 | 连接 | 客户端线程 | 时长 | 成功 req/s | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Round 0 epoll | 6 | 512 | 4 | 10 s | 217,960 | 0 |
| Round 0 epoll | 6 | 512 | 4 | 10 s | 196,696 | 0 |
| Round 2 epoll | 6 | 512 | 4 | 10 s | 213,041 | 0 |
| Round 2 epoll | 6 | 512 | 4 | 20 s | 209,547 | 0 |
| Round 3 epoll | 6 | 512 | 4 | 20 s | 208,834 | 0 |
| Round 3 io_uring | 6 | 512 | 4 | 10 s | 193,265 | 0 |
| Round 4 epoll | 6 | 512 | 4 | 20 s | 206,703 | 0 |
| Round 4 io_uring | 6 | 512 | 4 | 20 s | 192,597 | 0 |

Round 3 的 10 秒 epoll 复测为 `206,861 req/s`。Round 4 在加入 CPU/延迟采样后为 `206,703 req/s`；io_uring 为 `192,597 req/s`，没有超过 epoll。相同版本下的差异在 WSL2 中较明显，因此报告使用长时间结果和错误数，不把单次峰值当成稳定容量。线程扫参也显示：2 个服务线程约 `76k`，4 个约 `211k`，6 个约 `208k～213k`，8 个约 `186k`；当前硬件上继续增加线程没有收益。

### 回归验证

- Debug 构建：CTest `24/24` 通过。
- ASan/UBSan 构建：CTest `24/24` 通过。
- benchmark shell 脚本通过 `bash -n`。
- Python benchmark 通过 AST 语法检查。
- C++ 客户端只有完整、正确响应才计数，所有记录的高吞吐测试错误数均为 `0`。

高吞吐资源采样（512 个连接、4 个客户端线程、20 秒）显示：epoll `206,703 req/s`，p50/p95/p99 为 `1.100/2.250/3.150 ms`，服务进程消耗 `83.84 CPU s`，约 `419.1%` 单核占用，即整机 `34.9%`；io_uring `192,597 req/s`，p50/p95/p99 为 `1.250/2.525/3.350 ms`，消耗 `83.05 CPU s`，约 `415.1%` 单核占用，即整机 `34.6%`。因此两种后端均未打满 12 个逻辑 CPU，io_uring 当前约比 epoll 低 `7.3%`，且尾延迟略高。

## 4. 当前结论与未完成项

当前可以确认的是：Python 的约 8k QPS 不是服务器最大吞吐；在这台 WSL2 + Ryzen 5 6600H 环境中，Release epoll `/ping` 可以稳定达到 20 万 req/s 以上。不能据此推断 WebSocket、数据库路由、静态大文件、连接洪泛或其他宿主机的性能。

Phase 6 仍需补充 WebSocket 广播、连接洪泛、慢客户端、故障演练、`perf`/火焰图和正式发布检查。当前环境没有可用 `perf`，因此本记录只报告已验证的热点和结果，不声称已经完成系统级 profiling。io_uring 本轮已减少 CQE 临时分配并合并提交/等待，但在小包场景仍低于 epoll；主要剩余成本可能来自 poll/read/write 操作编排，后续需要基于 profiling 或更专门的 io_uring 状态机继续验证，不能仅凭猜测加入更复杂的 multishot/fixed-buffer 方案。

相关基准原始记录见 [Performance_Analysis.md](Performance_Analysis.md)，复跑方法见 [Benchmark.md](Benchmark.md)。

## 5. 应用端可用性完善

- 重做 `wwwroot/index.html` 的登录、注册和聊天室界面，去掉 JavaScript `alert` 作为主要反馈，改为页内错误、成功提示和 Toast。
- 增加登录态恢复、退出登录、JWT 失效处理、WebSocket 自动重连、连接状态和手动重试。
- 房间列表改为使用后端接口动态加载，支持搜索、空状态、创建房间和移动端侧边栏；首次没有房间时自动创建“综合大厅”。
- 消息输入支持 Enter 发送、Shift+Enter 换行、4096 字符限制、字符计数、当前房间切换和最近 100 条前端会话消息保留。
- 所有用户可控文字通过 DOM `textContent` 写入，避免将房间名、消息内容和服务端字段拼接进 HTML。
- 修复 `hidden` 属性被布局样式覆盖的问题，避免登录层和聊天层同时显示；通过临时静态服务完成登录页、表单校验和创建房间弹窗的浏览器回归。
- 第二轮视觉调整统一页面间距、边框、阴影和状态色，增加侧栏品牌区、房间数量、当前房间标识和更清晰的空状态；主操作使用蓝色，品牌标记使用珊瑚色，避免页面只剩单一色调。

当前后端没有消息历史接口，刷新页面后历史消息不会从服务器恢复；广播协议也没有发送者字段，因此其他用户的消息显示为“成员”。这两点属于后端协议能力，不在本轮前端改动中伪造。
